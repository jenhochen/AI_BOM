================================================================
  v0.09  2026-10-19
================================================================

【起因】

  SM8008 實際使用時，112 項 BOM 只命中 26 項，電容 32 項全軍覆沒。
  逐項比對 DB 後確認：**20 項是程式的錯，不是 DB 沒料**。

  根因是 Part 欄位格式變了：
      舊 BOM   4.7uF          只有容值
      SM8008   4.7uF/10V      容值/耐壓
               NC(47nF/10V)   NC 包在括號裡

  v0.08 是拿整串 Part 去 DB 的 Description 裡找子字串，格式一變就全找不到。
  而且比不到就靜默留白，所以**沒有人發現**，直到人工核對產出才看出來。

【新增 — 比對邏輯（R1～R7 通用規則）】

  不為單一元件打補丁，改成所有分支共用的規則：

  R1 正規化   先剝 NC 包裝，標記 nc 旗標
              支援 NC(x) / x/NC / NC/x / x_NC 四種寫法
  R2 切欄位   Part 以 / _ 空白 逗號 切段，第一個「解析得出數值」的段落＝主值
  R3 屬性辨識 其餘段落逐一認：耐壓 數字V／誤差 數字%／電流 數字A／
              直流阻抗 數字mR。**認不得的段落忽略但記錄**，不讓它害整筆比不到
  R4 數值化   容值→pF、阻值→Ω、電感→uH
              解決 0.47uF ≡ 470nF、4K7 ≡ 4.7K、300Ω ≡ 300R
  R5 封裝     必須相符（沿用現行 pkg_of）
  R6 方向性   耐壓／電流 **DB ≥ BOM**；誤差 **DB ≤ BOM**
  R7 診斷     未命中一律歸因並印出

  比對順序：先走屬性式，比不到才退回 v0.08 的子字串比對。
  也就是「只增不減」—— 舊 BOM 走得通的路徑完全沒動。

▌ R7 診斷（真正的預防機制）

  每次比對結束會印出未命中的原因分佈：

      未命中原因：
          主值解析失敗             2 項   例：CP_3020P
          規格不符（耐壓/電流/誤差）    11 項   例：4.7uF/10V
          值有但封裝不符            7 項   例：0.1uF/50V
          DB 沒有這個值          17 項   例：120pF/25V
          非標準件（IC/連接器等）     30 項   例：PCIe5 M.2 Gold Finger

  另外兩道警告：
    - 「主值解析失敗」會列出前 6 項，代表 Part 格式可能又變了
    - 某一類元件（C/R/L）達 5 項以上且**命中率 0%** 時醒目警告

  如果 v0.08 有這個，SM8008 一跑就會看到「32 項電容主值全部解析失敗」，
  當場就抓到，不必等到人工核對產出。

【新增 — 雙面板】

▌ 欄位（方案一：回歸 ADATA 範本原設計）

      單面板   F=Location-Top Layer    G:O=Knowledge Note
      雙面板   F=Location-Top Layer    G=Location-Bottom Layer
                                       H:O=Knowledge Note

  範本第 36 列本來就有 Location-Bottom Layer —— v0.06 當時是單面板，
  才把它改成 Knowledge Note。欄數維持 15（A:O），表頭、圖片區、
  外框線全部不用動。

▌ 位號 TOP/BOT 對照表

  格式：**第一欄＝位號，第二欄＝面別**。
  xlsx 為主要格式，txt 為選用。

  刻意**不看表頭名稱** —— 實際拿到的兩份檔案表頭就不一致：
      TXT   Location / T/B
      XLSX  Location / T_B
  面別接受 TOP / T / TOP SIDE / BOT / B / BOTTOM / BACK 等寫法。

  TXT 另做編碼自動偵測：有 BOM 照 BOM；沒有先試 UTF-8，失敗退 cp950。
  XLSX 另處理 Excel 把位號存成數字的狀況（1E5 會變 100000.0）。

▌ 位號對不上的三層處理

  SM8008 實測：BOM 位號 383 個、對照表 381 個，6 個對不上。

  ① 執行日誌列出受影響的項目與位號，整列全查不到的標 ★
  ② Excel 該列淡紅底（FDE1E1），H:O 欄寫出是哪幾個位號（紅字）
  ③ 反向檢查「對照表有、BOM 沒有」的也提示

  為什麼一定要吵：Item 77（240R_1%，Qty 4）的 4 個位號全部查不到，
  靜默略過的話 TOP=0、BOT=0，**4 顆電阻從兩面同時消失**，
  但 Qty 欄還是寫 4，產線備料會少 4 顆而且沒人發現。
  真正的成因是兩份檔案很可能不是同一個改版
  （對照表有 R46/R47/R51/R57 不在 BOM 裡，BOM 有 R48/R54 不在對照表）。

▌ PCB 圖片切兩半

      單面板   一張圖佔滿 rows 9-35（高 700px）—— 與 v0.08 完全相同
      雙面板   TOP 放 rows 9-21、BOT 放 rows 22-35，各高 340px，
               中間畫分隔線，左側標 TOP / BOT

  判斷依據＝有沒有找到兩張圖。檔名含 top / bot（可用 _ 或 - 分隔），
  例如 pcb_top.jpg / pcb_bot.jpg、SM8008-TOP.png / SM8008-BOT.png。
  雙面板但只有一張圖時，圖片區維持整塊不切半，並在日誌提醒。

【修正】

▌ C 案「重新掃描目錄」對原本是空的欄位沒有作用

================================================================
  v0.08  2026-10-15
================================================================

【起因】

  2026-10-14 SM8008 實際使用時，C 案與 D 案產出的兩份 Excel 完全不同：

      run_C_streamlit.bat  ->  SM8008_adata.xls
          45 主列 / Total Qty 101   <- 其實是舊的 S-M2P42280SMH086
      run_D_webview.bat    ->  BOM_SM8008_..._20261014.xlsx
          113 主列 / Total Qty 384  <- 正確的 SM8008

  比對後查出來不是程式輸出邏輯有差（版面格式 100% 相同），
  而是**兩邊餵進去的 Text BOM 根本不是同一份**。成因是下面的
  第 2、3 項連在一起：C 案沒有瀏覽功能，只能接受自動偵測的預設值，
  而預設值被排序 bug 指到了 2026-09-01 的舊範例檔。

【新增】

▌ 1. 標題列標出啟動用的批次檔

  同時開 C / D 兩個介面時，過去都叫「BOM Matcher v0.0x」分不出來。

      C 案  瀏覽器分頁標題   BOM Matcher v0.08  [run_C_streamlit.bat]
      D 案  原生視窗標題     BOM Matcher v0.08  [run_D_webview.bat]

  兩案的側邊欄副標也一併改成顯示啟動器名稱。

▌ 2. C 案補上檔案瀏覽功能（本來只有 D 案有）

  每個檔案欄位都加了兩種選法，雙保險：

      「瀏覽…」       原生檔案對話框（tkinter），與 D 案一致
      「📂 目錄瀏覽器」 純 Streamlit 元件，不依賴 tkinter

  為什麼做兩套：Streamlit 的指令碼跑在背景執行緒，tkinter 對話框
  偶爾會開在瀏覽器視窗後面、或在某些環境失效。目錄瀏覽器一定能用，
  顯示目前路徑、上一層、程式目錄捷徑、資料夾清單、符合副檔名的
  檔案清單（含最後修改日期）。

  輸出路徑欄位也加了「瀏覽…」（另存對話框），選完自動套 .xlsx。

▌ 3. 雙交付包（本版起每次更新都做，規格對齊 Firmware Tool）

      dist\BOM_Matcher_v0.08_完整離線安裝版\  + .zip   目標機器免上網
      dist\BOM_Matcher_v0.08_精簡版\          + .zip   目標機器要上網

  兩者都有「安裝.bat」與「安裝說明.txt」。
  產生腳本：toolsuild_dist.py（--refresh-wheels 可重抓套件）

▌ 4. 操作 SOP

  docs\BOM_Matcher_v0.08_操作SOP.pptx
  以 C 案與 D 案實機截圖製作。

【修正】

▌ 自動偵測的預設值是被副檔名順序決定的（本版主要 bug）

  v0.07 的 find_bom_txts() 先 glob *.txt 再 glob *.BOM，
  discover() 取 txts[-1] —— .BOM 檔永遠排最後、永遠被選中，
  跟檔名和日期都無關。實際後果：

      TXT\ 裡有三支檔案
        S-SM2268XT_...txt                 2026-06-12
        SM8008_...BOM.txt                 2026-10-14  <- 應該選這支
        S-M2P42280SMH086-20260812_1.BOM   2026-09-01  <- v0.07 選了這支

  修正：新增 _newest()，四個 find_*() 一律依最後修改時間由新到舊
  排序，discover() 改取 [0]。DB / Knowledge / PCB 圖片同樣處理
  （PCB 圖片仍維持 pcb.* 優先，其餘才依時間）。

▌ 輸出副檔名沒有強制 .xlsx

  使用者在輸出路徑打 .xls，openpyxl 仍寫出 OOXML 格式，產生
  「內容是 xlsx、副檔名是 xls」的檔案。Excel 會跳「格式與副檔名
  不符」警告，openpyxl / pandas 則直接拒絕開啟：

      InvalidFileException: openpyxl does not support the old .xls
      file format, please use xlrd to read this file

  實際事故：output/SM8008/SM8008_adata.xls 無法被任何工具讀取，
  我是複製成 .xlsx 才比對得出內容。

  修正：新增 force_xlsx()，write_excel() 開頭強制正規化副檔名，
  被更正時會在日誌印出提醒。

▌ 輸出被重導向時會因為 ✓ 字元當掉

  Windows 主控台預設 cp950，印不出 U+2713。輸出導到檔案或管線時
  （python bom_core_0.08.py > out.txt）會噴

      UnicodeEncodeError: 'cp950' codec can't encode character '✓'

  把整個程式打斷。.bat 有設 PYTHONIOENCODING 所以沒事，但直接用
  python 執行時沒有，而且 python -I（isolated mode）會忽略所有
  PYTHON* 環境變數。

  修正：不依賴環境變數，程式啟動時自己把 stdout/stderr
  reconfigure 成 UTF-8（errors='replace'）。

▌ C 案直接雙擊的提示（v0.07 修訂版已做，本版沿用）

  Streamlit 的 .py 必須用 streamlit run 啟動，直接執行只會噴
  missing ScriptRunContext 然後結束，使用者看到的就是閃退。
  現在會印出「請改用 run_C_streamlit.bat」並停住等按鍵。

【修正】

▌ 框線消失問題（核心修正：合併儲存格的邊界框線分配方式）

  根本原因：
    Excel 渲染合併儲存格的框線時，是依據範圍內「每一個儲存格」各自
    的框線設定來決定該邊界是否畫線，而不是只看左上角錨點儲存格。
    v0.04 的 _cell() 只把框線設定在合併範圍的錨點儲存格上
    （例如 K7:L8 合併時，只設定 K7 的框線），導致：
      - 合併範圍「下邊界」「右邊界」對應的儲存格（K8、L8 等）
        完全沒有框線 → 該邊界在 Excel 中完全不顯示。
    這正是三個回報問題的共同成因：

    (a) 表格最右邊和底部框線消失
        → PCB 圖片區（rows 9-35）原本完全沒有設定任何框線；
          資料區與表尾也只用統一的 thin 框線，且最後一列
          沒有「封閉」用的 medium 底線。

    (b) 環保等級所在列(row 8)下方框線消失
        → K7:L8、M7:O8 為兩列合併儲存格，框線只設在 K7/M7，
          下邊界儲存格 K8/L8/M8/N8/O8 完全沒有框線。

    (c) Total 列與 Approval 列之間框線消失
        → 表尾（Remark / 圖例 / Approval）區域沒有延續外框
          medium 框線，造成 Total 列以下視覺上「斷開」。

  修正方式：
    - 新增 _set_box() 通用函式，取代舊有的 _cell()：
        merge_cells() 之後，將傳入的 Border 依範圍邊界正確
        分配到每個邊界儲存格：
          左邊界(c==c1)的所有列 → 套用 border.left
          右邊界(c==c2)的所有列 → 套用 border.right
          上邊界(r==r1)的所有欄 → 套用 border.top
          下邊界(r==r2)的所有欄 → 套用 border.bottom
    - PCB 圖片區（rows 9-35）：A欄(左)、O欄(右)逐列套用
      medium 外框，使整份文件外框連續不中斷。
    - 表尾區（Remark/圖例/Approval）：全部列改用 B_FOOT；
      最後一列套用 medium 下框線封閉整張表格。
    - 環保等級 (K7:L8 / M7:O8)：_set_box() 一次性處理，
      下邊界 (row 8) 自動取得 medium 框線。

  驗證結果：
    ✓ 所有列 A欄左框線 / O欄右框線：完整無缺漏
    ✓ 最後一列：A:O 全部 bottom=medium（封閉表格）
    ✓ row 8（環保等級）：K/L/M/N/O 全部 bottom=medium
    ✓ Total 至 Approval：A-left / O-right 連續 medium，無斷線
    ✓ 合併儲存格衝突數：0

【新增函式】
  - _set_box()：通用合併/單一儲存格寫入，框線 Excel 100% 相容
  - B_OUTER / B_TOPCAP / B_BOTCAP / B_BODY_L / B_FOOT：預設框線樣式常數

【移除】
  - 舊版 _cell() 輔助函式（已被 _set_box() 取代）

【修正】

▌ Excel Merge 衝突修正（主因：Excel 開啟時出現「已進行修復」警告）

  根本原因：
    v0.03 的 _build_header() 對 rows 3-8 跑同一個 loop，
    在 row 8 時建立了 K8:L8 與 M8:O8；
    loop 結束後又對 row 7 執行：
        unmerge('K7:L7') → merge('K7:L8')   ← 此時 K8:L8 殘留未清除
        unmerge('M7:O7') → merge('M7:O8')   ← 此時 M8:O8 殘留未清除
    結果 XML 中同時存在：
        K7:L8  ↔  K8:L8   (子集衝突)
        M7:O8  ↔  M8:O8   (子集衝突)
    Excel 偵測到衝突 → 觸發自動修復。

  修正方式：
    - 將 rows 7-8 完全移出 loop，單獨處理
    - Row 7 左側：merge A7:C7、D7:J7
    - Row 8 左側：merge A8:C8、D8:J8
    - 右側一次建立 K7:L8 與 M7:O8（2-row span，不做 unmerge）
    - 完全消除 unmerge/re-merge 操作
  驗證結果：Conflicting merge pairs = 0

▌ PCB 圖片嵌入方式改為 simple cell anchor
  - 移除 TwoCellAnchor / AnchorMarker 用法（相容性較差）
  - 改用 ws.add_image(img, 'A9') + 顯式設定 width/height

    python bom_core_0.07.py                              全自動
    python bom_core_0.07.py -o out.xlsx
    python bom_core_0.07.py BOM.txt db.xlsx -k Knowledge.xlsx -p pcb.jpg
    python bom_core_0.07.py --no-split                   關閉替代料拆列
